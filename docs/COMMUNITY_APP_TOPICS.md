# AnimeVault 4.1.5 — собственные темы обсуждений (первая стадия)

## Что меняется

Android выводит идентификатор обсуждения из каталога **AnimeVault**. Просмотр и публикация комментариев больше не требуют запроса к Kodik, Yummy, AniMetka, AniLiberty, Shikimori, MAL или AniList **на сервере**. Кодик остаётся исключительно источником видео. Существующие профили, комментарии, лайки, жалобы, RLS и механика авторизации продолжают работать на том же Supabase.

Алгоритм ключей (v1):
1. Из локальных метаданных присутствует MAL ID или Shikimori ID → `av1:mal:<id>`. Одна ветка для разных видеопровайдеров с совпадающим ID.
2. Иначе присутствует AniList ID → `av1:anilist:<id>`.
3. Иначе нормализованное английское название, либо название карточки, и год → `av1:title:<SHA-256>`. Не использовать название как **доказательство** совпадения: разные названия/транслитерации не обязаны сливаться, похожие могут требовать ручной коррекции.

Первый зарегистрированный пользователь создаёт каноническую запись в собственной таблице `community_app_topics` через `community_app_open`. Неавторизованным функция возвращает стабильный контекст без единой записи в базу, чтобы показывать пустую ленту и предложение авторизоваться. Вход и профиль необходимы для отправки комментария, как и раньше.

Нумерованные серии получают `regular:12` (или `fractional:12.5`), отдельные без нумерации — ключ из названия/идентификатора, без объединения непроверенных эпизодов. Темы аниме и эпизодов сохраняют разные UUID. Ответы, рейтинги и модерация идут через старые `community_create_comment`, `community_list_comments` и прочие RPC.

## Безопасность и ограничения

- Ни один внешний API/token не участвует в новом `community_app_open`.
- Только `SECURITY DEFINER` с фиксированным `search_path`, проверкой ключа, эпизода, блокировок, RLS и отсутствием прямых GRANT на новую таблицу.
- Создание доступно только авторизованным пользователям; 20 новых тем/час, 80/сутки на пользователя. Повторное открытие уже созданной темы квоты не расходует.
- Присвоение существующего канонического anime_id допускается только по точному уже записанному MAL/AniList ID. Никакие verified provider aliases и доверенные имена не меняются.
- Ранее созданные комментарии не удаляются и не мигрируют. Провайдер-специфичный `community-ensure` остаётся для совместимости со старыми клиентами, **новая онлайн-вкладка его не вызывает**.
- Первичная версия не обещает автоматического совпадения всех транслитераций и версий названий; для этого нужен отдельный модерируемый справочник соответствий и механизм слияния.

## Порядок ввода в производство — обязательный

**Нельзя публиковать APK 4.1.5 до применения миграции 003.**

1. Сначала объедините серверную часть миграции с проверенными тестами в main либо используйте единый PR, но до публикации APK 4.1.5 примените SQL в защищённом workflow. Он работает только в main.
2. В GitHub → Actions → Supabase migrations запустите `check` на `main`. Убедитесь, что pending — **только** `202611020003_community_app_topics.sql`, старые объекты без drift/блокировок.
3. Через тот же workflow запустите `apply` с требуемым plan hash и фразой `APPLY kgvkxocbkklisqrqmcjx`; одобрите protected production environment. SQL старые таблицы не удаляет.
4. Проверьте `app_topics.state = complete` в Summary и миграцию `202611020003` в history. Только затем публикуйте APK 4.1.5 (85) и проверяйте реальный гостевой/авторизованный проход.
5. Проверки: открытие карточки без Community Auth → пустая лента и предложение войти; авторизованный пользователь → одна тема; один и тот же MAL ID через два источника → один UUID; повторный вход → тот же UUID; серии 1/2 → разные UUID; ответы/лайки/жалобы работают; остановка функции не нарушает работу плеера.

Откат Android возможен, поскольку базовые RPC и данные сохранены. Миграция аддитивная; **не удалять таблицу для отката**, иначе возникнут ссылки на уже созданные комментарии.
