# Настройка существующего Supabase

Для существующего проекта AnimeVault используйте [миграции через GitHub Actions](SUPABASE_MIGRATIONS.md): проверка истории, учёт вручную применённой 001 и безопасное применение/восстановление 002 без копирования SQL в редактор. Запись требует отдельного подтверждения.

Проект AnimeVault: `kgvkxocbkklisqrqmcjx`, eu-north-1, `https://kgvkxocbkklisqrqmcjx.supabase.co`. Не создавать второй проект. Не включать Google OAuth, anonymous sign-in, linking или CAPTCHA без отдельного решения владельца.

## Конфигурация Android

Передать через переменные окружения сборки либо Gradle properties вне Git:

```text
SUPABASE_URL=https://kgvkxocbkklisqrqmcjx.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
COMMUNITY_ENABLED=true
```

В workflow сборки используются одноимённые GitHub repository **variables**. Publishable key не является серверным секретом. Service role, secret key, Management API token, пароль PostgreSQL, SMTP credentials и личные refresh tokens в Android запрещены. При неверном URL/ключе либо отключённом флаге Community недоступно, остальные экраны работают. Без ключа функция недоступна; с корректным ключом и без явного флага включается автоматически. Явный false отключает её. С 4.1.1 доверенный workflow использует выданные владельцем публичные параметры как fallback. См. [пошаговый запуск](COMMUNITY_LAUNCH.md). Никакая сборка не требует сетевого доступа к Supabase.

Secret-free PR workflow создаёт синтетический нерабочий Firebase config только для компиляции и тестов, не публикует APK и не читает repository secrets. Реальный подписанный тестовый APK собирает существующий `build-apk.yml` на этой feature-ветке, с прежними Firebase restore, keystore, проверками подписи и версии. Он не публикует Release для feature-ветки. Нужны уже настроенные владельцем Firebase/signing secrets.

## Безопасное применение миграции владельцем

1. Проверить SHA PR, результаты SQL CI, diff миграции и отсутствие конфликтующих `community_*` объектов. Проверить версию PostgreSQL, текущие schema grants и настройки PostgREST.
2. Сделать резервную копию существующей БД и проверить восстановление в изолированном окружении. Сохранить настройки Auth отдельно, без помещения секретов в Git.
3. Сначала воспроизвести миграцию `supabase/migrations/202611010001_community.sql` в отдельном тестовом окружении. Тест `tools/test-community-database.py` допускает только loopback disposable PostgreSQL и сам создаёт Auth shim — **его нельзя запускать на Supabase или существующей БД**.
4. Согласовать окно изменений. В Supabase SQL Editor существующего проекта выполнить ровно содержимое миграции от `begin` до `commit` как владелец БД. Не запускать `db push`, reset или автоматический CI deployment. Миграция одноразовая, отслеживается по имени в журнале владельца/истории миграций; повторное применение отвергается.
5. При ошибке транзакция должна быть отменена (`rollback` при необходимости). Проверить отсутствие частичных объектов до исправления и повторения. Не удалять существующие объекты вслепую.
6. Проверить RLS и GRANT по [SUPABASE_SECURITY.md](SUPABASE_SECURITY.md), обновление schema cache PostgREST и доступность разрешённых RPC с publishable key для гостя. Проверить, что приватные таблицы недоступны напрямую.
7. Назначить первого администратора доверенным SQL и завести проверенные канонические связи, см. [COMMUNITY_MODERATION.md](COMMUNITY_MODERATION.md).
8. Включить Community в тестовой сборке, проверить два аккаунта и гостя, Firebase и AniList отдельно. Не включать публичную регистрацию до выполнения условий ниже.

## Email, redirect и recovery

Auth уже настроен: Email, confirm email, secure email/password changes, current password requirement; минимум 12 символов с буквами/цифрами, OTP 8 цифр на 3600 секунд. Не ослаблять эти параметры для прохождения тестов.

Signup и recovery передают `redirect_to=animevault://auth/callback` и PKCE S256. Verifier сохраняется зашифрованно на устройстве, поэтому письмо открывают на том же устройстве. Проверяются точные scheme/host/path, отсутствие fragment/произвольных bearer tokens, единственный code, срок и назначение ожидающего запроса. Локальный verifier связывает обмен кода с инициированным потоком; произвольный `state` из Intent не используется как доверенное подтверждение. Один ожидающий email-поток на установку; новое письмо заменяет предыдущее ожидание.

Если redirect открыл браузер, вернуться в аккаунт Community и ввести email и 8-значный OTP. Шаблоны confirmation/recovery должны действительно включать `{{ .Token }}` для этого fallback. Не редактировать Auth Secrets. Recovery даёт отдельное состояние ввода нового пароля. Проверить на реальном сервере сочетание recovery, Secure password change и Require current password: отказ сервера отображается пользователю, настройки не обходятся и не отключаются. Для дополнительной проверки поддержаны GET reauthenticate и ввод nonce из письма. Любой неподдержанный ответ или отказ recovery блокирует выпуск до доработки и повторной проверки.

`http://localhost:3000` — временный Site URL. Явный redirect не заменяет корректный production fallback. Владелец должен установить HTTPS Site URL со страницей восстановления/инструкцией, проверить allowlist redirects и шаблоны писем. Этот PR не разворачивает веб-страницу.

**Публичный запуск регистрации заблокирован до внешнего SMTP.** Встроенный сервис ограничен двумя письмами в час на проект и разрешёнными адресами команды. Настроить внешний SMTP в панели владельца, DNS SPF/DKIM/DMARC, доставку, ограничения и мониторинг. Для сборки APK SMTP не требуется. Параметр captcha token предусмотрен в Auth repository; CAPTCHA пока отключена, UI получения challenge не добавлен.

Custom scheme не обеспечивает эксклюзивное владение ссылкой. Перед production настроить проверенный HTTPS-домен, Android App Links, `assetlinks.json` с package/signing fingerprints и соответствующий intent-filter `autoVerify`, обновить redirect allowlist и клиентскую валидацию. Проверить холодный и тёплый запуск, перехват другой программой и OTP fallback. Без реального устройства безопасность/работоспособность callback не считается подтверждённой.

## Откат и восстановление

Быстрое отключение — `COMMUNITY_ENABLED=false` в следующей сборке (не дистанционный kill switch уже установленного APK). До распространения исправления владелец может временно отозвать EXECUTE новых RPC/доступ Data API, сохранив данные и отдельный Auth. Не трогать Firebase, AniList и медиатеку.

Обратной разрушительной SQL-миграции нет: при принятой транзакции данные сохранять, исправлять новой миграцией. В случае повреждения восстанавливать backup в отдельный проект/БД, сверять таблицы и данные, затем согласовать точечное восстановление. DROP/TRUNCATE и удаление Auth users не являются обычным откатом функции Community. Сохранять журнал применённого SHA и SQL, время, результаты проверок и ответственного владельца.
