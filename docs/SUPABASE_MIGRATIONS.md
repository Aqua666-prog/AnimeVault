# Миграции Supabase через GitHub Actions

SQL больше не нужно копировать в мобильный SQL Editor. Workflow **Supabase migrations** работает только через ручной `workflow_dispatch` из `main`, для проекта `kgvkxocbkklisqrqmcjx`. По умолчанию он проверяет состояние без записи. Никаких Gradle, APK, Release, db reset, seed или загрузки roles.sql в этом workflow нет.

## Однократная настройка с Android-телефона

1. Объедините PR автоматизации. Откройте GitHub в браузере; для настроек при необходимости включите «Версия для ПК».
2. В Supabase откройте **Connect → Session pooler → URI**, порт **5432**. Прямое подключение `db.kgvkxocbkklisqrqmcjx.supabase.co:5432` также поддерживается, но обычный GitHub runner может не иметь нужного IPv6. Не используйте transaction pooler на 6543.
3. GitHub → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**:
   - `SUPABASE_DB_URL`: URI подключения. Можно оставить `[YOUR-PASSWORD]` из панели Supabase или убрать пароль из URI. Имя пользователя pooler должно быть `postgres.kgvkxocbkklisqrqmcjx`, база — `postgres`; host возьмите из своего Connect, не угадывайте региональный адрес.
   - `SUPABASE_DB_PASSWORD`: текущий пароль PostgreSQL, введённый непосредственно в поле Secret. Спецсимволы автоматически кодируются; самостоятельно менять пароль или кодировать его не нужно. Это не publishable key, service_role JWT или пароль Community-пользователя.
   - **Обязательно `SUPABASE_DB_CA_CERT`**: полный PEM CA из **Supabase → Database Settings → SSL Configuration → Download certificate** для этого проекта. Вставьте содержимое файла, включая строки `BEGIN CERTIFICATE` и `END CERTIFICATE`, в многострочный Secret. Это публичный сертификат CA, а не приватный ключ и не пароль. Runner проверяет формат, CA-признак и срок действия, затем объединяет сертификат с системными CA в один временный bundle для psycopg и CLI. Проверка TLS всегда `verify-full`; отключать её нельзя.
4. **Settings → Environments → New environment → `supabase-migrations-production`**: разрешите только `main`, включите required reviewers и проверку владельцем, если ваш тариф GitHub поддерживает защиту environment. При желании продублируйте эти Secrets в environment; они должны вести в тот же проект, иначе повторная проверка остановит запись.
5. Не присылайте пароль/URI с паролем в чат, Issue или PR. Не включайте Actions debug logging и не запускайте CLI вручную с печатью аргументов. Отдельный Supabase Management token не нужен: CLI работает через PostgreSQL URL.

Workflow отклоняет URI другого проекта, неожиданные параметры подключения, неизвестные migrations и запуск не из `main`. Пароль находится только в GitHub Secrets и памяти runner. CLI stdout/stderr не публикуются: даже ошибка подключения может содержать пароль или SQL. В лог/артефакт выводятся только безопасные коды, имена объектов, версии и хеш плана.

## Первый запуск — только проверка

**Actions → Supabase migrations → Run workflow → Branch: main → action: check → Run workflow.** Поле confirmation оставьте пустым.

Откройте Summary и артефакт `migration-check` → `migration-report.json`:

| Поле | Значение |
|---|---|
| `history` | Реальные версии в `supabase_migrations.schema_migrations`; отсутствие таблицы истории означает пустую историю, а не отсутствие Community |
| `history_to_adopt` | Уже существующие точные схемы, для которых нужно только зарегистрировать версию |
| `pending_sql` | SQL-файлы, которые действительно предстоит выполнить; `001` здесь никогда не появляется |
| `autosync.state` | `absent`, `complete` или `partial_or_drift` |
| `missing`, `structure_drift`, `security_drift` | Недостающие объекты и обнаруженные различия |
| `blockers` | Причины, запрещающие применение и автоматическое восстановление |
| `plan_hash` | Отпечаток файлов, структуры/прав и истории; проверяется повторно непосредственно перед записью |

Проверяются определения колонок, ограничений, индексов, RLS-политик, триггеров, функций, владельцев, SECURITY DEFINER/search_path, публичных и эффективных прав anon/authenticated. Для закрытых объектов AutoSync проверяются и права service_role. Данные профилей, пользователей, комментариев и пароли не читаются. Контрольное соединение и CLI check/list/dry-run используют `default_transaction_read_only=on`; проверка не создаёт даже таблицу истории.

Наличие 11 таблиц/RLS само по себе **не считается доказательством**, что миграция полностью применена. Эталон `tools/supabase_migrations/reference.json` получен из неизменённых миграций на изолированном PostgreSQL 17 и связан с SHA-256 каждого файла. Строгое сравнение может потребовать дополнительного разбора на другой версии PostgreSQL или при легитимных ручных изменениях. Workflow не пытается «исправить» такое расхождение автоматически.

## Применение после проверки и явного разрешения

Снова **Run workflow**, выберите `action: apply` и введите точно:

`APPLY kgvkxocbkklisqrqmcjx`

Сначала снова выполняется check. Затем, после environment approval, write-job повторно сравнивает план с проверенным отпечатком. Если история/схема поменялась между проверкой и подтверждением, запись останавливается: запустите новую проверку и рассмотрите новый отчёт. Неправильная confirmation останавливает workflow без записи; `check` никогда не запускает write-job.

- `001` уже была выполнена вручную: если схема соответствует эталону, CLI выполнит **только** `migration repair 202611010001 --status applied`. Таблицы, функции и данные повторно не создаются. Если запись истории уже есть, repair пропускается. При несовпадении базовой схемы workflow останавливается и не выполняет старую миграцию.
- Если `002` полностью отсутствует: после учёта `001` CLI показывает dry-run и выполняет только `002`.
- Если `002` полностью соответствует эталону, но истории нет: CLI регистрирует `002` через single-version `repair --status applied`; SQL не выполняется повторно.
- Если всё уже применено: повторный запуск не меняет историю или объекты.
- Если `002` частичная: обычный `apply` останавливается. Сначала рассмотрите восстановление ниже.

Артефакт `migration-result` и Summary показывают итоговую историю и сверку структуры. После успешного запуска ожидаются обе версии, `autosync.state: complete`, пустые `blockers`, `missing` и drift. Добавлены две служебные таблицы с RLS и один RPC, как в PR #35; каталог аниме этим workflow не заполняется. Следующий шаг — отдельный **Community Catalog AutoSync**.

## Частично применённая 002: безопасное восстановление

Сначала всегда выполняйте `check`. Ничего не удаляйте и не используйте `repair --status reverted`, db reset или повтор старого файла целиком.

Если базовая схема точная, существующие объекты `002` имеют ожидаемую структуру, история ещё не объявляет `002` применённой, и нет неизвестных объектов/версий, можно выбрать **action: recover** с той же точной confirmation. Отчёт check перед этим должен быть рассмотрен владельцем.

`recover` составляет временный план из исходной `002`:

- создаёт только недостающие таблицы;
- сохраняет строки и существующие таблицы;
- включает ожидаемую RLS и восстанавливает предусмотренные REVOKE/GRANT;
- создаёт отсутствующий RPC либо использует CREATE OR REPLACE для существующего RPC с уже совпадающим телом/сигнатурой; затем восстанавливает owner/search_path/SECURITY DEFINER и права из миграции;
- выполняет этот план и регистрацию `002` одной транзакцией CLI, после чего сверяет состояние ещё раз.

При изменённых колонках/ограничениях/индексах/политиках/теле функции, другом владельце таблицы, изменённой FORCE RLS, неизвестных объектах или уже записанной `002` с несовпадающей схемой восстановление **блокируется**. Сохраните безопасный отчёт и подготовьте отдельное проверенное аддитивное исправление в PR. Это намеренная граница автоматизации: workflow не удаляет данные, не угадывает структуру и не фальсифицирует историю ради зелёного результата. Копировать SQL в редактор для диагностики не требуется.

## Транзакции, ошибки и повторные запуски

Закреплён Supabase CLI **2.54.11**; его реальное поведение проверено интеграционными тестами. CLI исполняет batch миграции и INSERT истории в неявной транзакции. Исходные файлы содержат собственные BEGIN/COMMIT: чтобы не разорвать атомарность перед записью истории, runner парсит SQL через pglast и удаляет **только внешние** маркеры в изолированном временном каталоге. Тела функций, Unicode и внутренние точки с запятой сохраняются. Исходные миграции в Git не меняются.

Для любого push временный файл `001` заменён на аварийный sentinel, который всегда выдаёт ошибку, если CLI неожиданно попытается повторить baseline. Только для single-version repair runner временно читает исходную `001`, чтобы история содержала настоящий SQL ранее выполненной миграции; repair не исполняет его.

Каждая новая миграция и её история атомарны. Регистрация ранее выполненной `001` может успешно завершиться до ошибки `002`; это корректно. При отказе SQL или INSERT истории новые объекты этой миграции откатываются. Автоматического destructive rollback нет. При потере соединения исход может быть неизвестен: сначала `check`, затем повторный разрешённый запуск. При неожиданном postflight mismatch остановитесь и рассмотрите отчёт, не стирая историю.

Workflow concurrency и advisory lock сериализуют запуски этого runner. Другие ручные администраторские сессии этим lock не связаны: не выполняйте параллельно ручной SQL/db push. Отдельный workflow AutoSync лучше временно не публиковать во время первичного восстановления. Само применение миграции не включает переменные разрешения AutoSync и не импортирует аниме.

## Поддержка и тестирование

- Основной runner: `tools/supabase_migrations/manage.py`.
- Ручной workflow: `.github/workflows/supabase-migrations.yml`.
- Изолированные тесты: `.github/workflows/supabase-migration-tests.yml`, без production Secrets и без Android-сборки.
- Проверенные файлы: `supabase/migrations/202611010001_community.sql` и `supabase/migrations/202611010002_community_autosync.sql`.

Добавление следующих миграций требует обновления проверенного эталона и allowlist runner в том же PR с тестами. Не включайте произвольный SQL по пути из workflow input. Обновление CLI также требует повторной проверки TLS, read-only режима и атомарности DDL/истории. В production TLS принудительно задан и в URI, и через PGSSLMODE/PGSSLROOTCERT: закреплённый CLI пересобирает URI внутри себя. Read-only параметр CLI также принудительно передаётся в startup options URI: одного PGOPTIONS для закреплённого CLI недостаточно.

Тесты используют только loopback PostgreSQL с минимальными auth/role-заглушками и настоящий закреплённый CLI: проверка без записи, ручная baseline/002 без истории, повторный запуск, частичная таблица с сохранением строки, запрет структурного drift, конфликт истории, смена плана, SQL-ошибка и ошибка INSERT истории с полным откатом новых объектов. Это не проверка реальной базы владельца и не заявление, что настройки Secrets уже завершены.


## TLS: исправление tls_certificate_verification_failed

В неудачном check [41386027177](https://github.com/Aqua666-prog/AnimeVault/actions/runs/41386027177) `SUPABASE_DB_CA_CERT` был пустым. Предыдущий код использовал только системный CA-файл; если Secret задавался, он заменял весь системный trust store. Это не обеспечивает нужную цепочку доверия для всех Supabase endpoints. [Официальная инструкция Supabase](https://supabase.com/docs/guides/platform/ssl-enforcement#connecting-to-your-database-with-ssl) требует добавить скачанный Supabase CA при использовании verify-full и показывает пример shared pooler.

Теперь владелец явно задаёт CA проекта, а runner объединяет его с системными корневыми сертификатами. Так сохраняется доверие как к Supabase CA, так и к публичным CA, которыми может подписываться pooler. Произвольные CA из URI/сетевых ответов не скачиваются и не добавляются автоматически. Временный bundle доступен только текущему runner и удаляется после выполнения. URI и PGSSLROOTCERT указывают на один и тот же bundle; verify-full и проверка hostname обязательны.

Если пароль и Session pooler URI уже верны, **менять SUPABASE_DB_URL и SUPABASE_DB_PASSWORD не нужно**. Добавьте/обновите только SUPABASE_DB_CA_CERT в repository Secrets. Если environment `supabase-migrations-production` содержит одноимённый Secret, обновите и его, чтобы apply позднее использовал тот же CA. CA не нужно помещать в APK или исходники.

С телефона: после слияния исправления откройте **Actions → Supabase migrations → Run workflow → main → action: check**, confirmation оставьте пустым. Нужен **новый запуск**, не Re-run старого failed run: повтор старого запуска использует старый commit. В Summary появится результат read-only проверки либо безопасный код:

- `supabase_ca_missing_download_from_database_settings` — Secret CA отсутствует;
- `supabase_ca_invalid_pem` / `supabase_ca_must_be_ca_certificate` — вставлен неверный файл, не полный PEM или серверный сертификат вместо CA;
- `supabase_ca_expired` / `supabase_ca_not_yet_valid` — недействительный CA, скачайте актуальный из Dashboard;
- `tls_ca_untrusted` — цепочка сервера не завершается доверенным CA;
- `tls_certificate_hostname_mismatch` — имя endpoint не соответствует сертификату; проверьте URI в Connect, не заменяйте hostname на IP;
- `tls_certificate_expired_or_not_yet_valid` — серверный сертификат/цепочка вне срока действия; не обходите проверку;
- `tls_certificate_verification_failed` — libpq не раскрыл точную причину, а безопасная дополнительная TLS-проверка не смогла её уточнить.

При общей TLS-ошибке libpq runner может выполнить дополнительный SSLRequest к тому же endpoint, чтобы получить код OpenSSL: это только TLS handshake без Auth, startup-пакета, SQL и записи. Пароль и полная строка подключения не выводятся. Исходный старый лог не содержит verify_code; точная цепочка удалённого endpoint из среды Codex не проверена из-за недоступности DNS/сетевого доступа к pooler. Поэтому ошибка отсутствующего CA устранена в конфигурации, но успешный check реального проекта должен подтвердить новый запуск владельца.

Регрессионные тесты создают временные CA/ключи и TLS endpoint только на loopback. Настоящие libpq и Supabase CLI проверяют bundle; отдельно проверяются чужой CA, неверный hostname, просроченный leaf, отсутствие/некорректный Secret и сохранение read-only startup options. Тестовые приватные ключи генерируются на время теста и не сохраняются в Git/артефактах.
