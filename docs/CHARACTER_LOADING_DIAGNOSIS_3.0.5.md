# Персонажи в 3.0.5 (65): подтверждённая ошибка поиска Аниметки

Проверено 23 октября 2026 года. Исследуемая база: `5e62919` (`main`, после PR #11).
Проверялись исходники и публичные HTTP API. Приложение, Gradle, Android SDK,
эмулятор и APK не запускались; сборка не выполнялась.

## Первопричина

В предыдущем исправлении в `ANIMETKA_SEARCH_ATTRIBUTES` были добавлены `mal_id`
и `anilist_id`. API Аниметки не принимает эти поля в проекции поиска.
В реальных запросах для Bleach, «Блич» и Naruto список полей из 3.0.5 возвращает
HTTP 500 с JSON `{"success":false,"error":"Server error!"}`. Удаление только
этих двух полей даёт HTTP 200. Каждое поле по отдельности также вызывает HTTP 500.

Для тайтла другого провайдера резервный путь сначала ищет внутренний ID Аниметки.
Ошибка поиска прерывает его **до** `GET /api/anime/{animetkaId}/characters`.
Поэтому одного наличия резервного источника было недостаточно: он вызывался,
но не доходил до списка персонажей. Предыдущие фиктивные API принимали любой
`attributes`, поэтому этот дефект контракта не обнаруживался тестами.

Второй подтверждённый дефект диагностики: `loadSource` перехватывал исключения
и возвращал `null`, теряя источник, этап и HTTP-код. На экран попадало общее
«Проверьте соединение», одинаковое для HTTP 500, отсутствующего ID и отключённого
источника. Эта формулировка не доказывала проблему с соединением пользователя.

Пользователь уточнил источник карточки: **Kodik**. Именно карточки Kodik идут
через этот поиск ID Аниметки. Поэтому дефект относится к указанному пользователем
пути, а не только к абстрактному примеру. Это воспроизведённый дефект кода 3.0.5
и внешнего контракта, не вывод только по сообщению на экране. Без лога устройства
нельзя подтвердить фактически переданные ID и исключить дополнительные локальные
проблемы. Для родной карточки Аниметки поиск ID пропускается.

## Доказательства

Полный журнал безопасных метаданных запросов: [character-loading-http-evidence.json](character-loading-http-evidence.json).
В нём сохранены URL публичных ресурсов, метод, время UTC, код, размер и SHA-256
полного ответа до сокращения фикстур. Заголовки, cookies, токены и HTML не сохранены.

| Запрос | Результат |
| --- | --- |
| Поиск Bleach, «Блич», Naruto с проекцией 3.0.5 | HTTP 500 у всех трёх |
| Те же поиски без `mal_id` и `anilist_id` | HTTP 200 у всех трёх |
| Повтор Bleach/Naruto с проекцией из исправленного Kotlin-файла | HTTP 200; совпали 269→2529 и 20→3061 |
| Bleach с `animetka_id`, `shikimori_id`, `mal_id` | HTTP 500 |
| Bleach с `animetka_id`, `shikimori_id`, `anilist_id` | HTTP 500 |
| Карточка Аниметки `2529` | HTTP 200, `id=2529`, `shikimori_id=269` |
| Персонажи Аниметки `2529` (Bleach TV-1) | HTTP 200, 293 записи |
| Карточка Аниметки `3061` | HTTP 200, `id=3061`, `shikimori_id=20` |
| Персонажи Аниметки `3061` (Naruto TV-1) | HTTP 200, 268 записей |
| Контроль: персонажи Аниметки `2778` (Frieren) | HTTP 200, 62 записи |
| POST Shikimori GraphQL, запрос приложения, `ids=269` и `ids=20` | HTTP 522 у обоих |
| Постер Ичиго на `shikimori.io` | HTTP 200, image/jpeg, 176 247 байт |
| Постер Ферн на `shikimori.io` | HTTP 200, image/jpeg, 28 398 байт |

В успешных поисках первый результат — другой тайтл (например, фильм), а не целевой
телесериал. Поэтому брать первый результат или подставлять Shikimori ID в маршрут
Аниметки нельзя. Реально подтверждены соответствия:

| Аниме | Shikimori anime ID | Animetka anime ID | MAL anime ID в проверенных карточках |
| --- | --- | --- | --- |
| Bleach TV-1 | 269 | 2529 | отсутствует |
| Naruto TV-1 | 20 | 3061 | отсутствует |
| Frieren TV-1 | 52991 | 2778 | отсутствует |

В полном списке Bleach проверены все 293 ID/имени; в Naruto — все 268. Невалидных
обязательных ID/имён не найдено. У одного персонажа Bleach нет постера: это допустимый
`null`, который не должен удалять самого персонажа. В первом персонаже Bleach
`character_shikimori_id=5` — это ID персонажа, не ID аниме и не доказательство MAL ID.

## Полный путь вызовов и ID

1. `OnlineTitleRoute` получает `uiState`; `OnlineTitleScreen` передаёт данные в
   `OnlineTitleExtrasSection`. Секция отображается на вкладке дополнений.
2. `OnlineTitleViewModel.retry()` загружает карточку через
   `OnlineRepository.getRelease(providerId, releaseId)` и вызывает `loadExtras`.
   Запросы начинаются после загрузки карточки, а не только после нажатия вкладки.
3. Провайдер формирует `OnlineReleaseDetails.externalIds`. Kodik заполняет
   `shikimoriId` из `item.shikimoriId`, а не из общего `release.id`; парсер Аниметки
   читает `id/animetka_id` отдельно от `shikimori_id`. Объединённый провайдер
   переносит пространства внешних ID раздельно. У остальных провайдеров ID могут
   отсутствовать; номер карточки сам по себе внешним ID не становится.
4. `loadExtras` вызывает `TitleExtrasRepository.getExtras`. Репозиторий запускает
   дополнительные источники и ждёт `ShikimoriExtrasRepository.getExtras`.
5. Shikimori делает `POST https://shikimori.one/api/graphql`: при известном
   `externalIds.shikimoriId` отправляет `variables.ids`, иначе ищет по названию.
   MAL ID не подставляется в поле Shikimori `ids`. Ошибка выбрасывается из загрузчика.
6. При `shikiExtras == null` или пустых `characters` запускается
   `AnimetkaExtrasRepository.charactersFor`. Это реальная существующая резервная
   ветка; её наличие проверено по коду, а вызовы закреплены новыми тестами.
7. Для `providerId == ANIMETKA` используется родной `release.id`. Для других
   провайдеров `resolveAnimetkaId(requireExternalId=true)` делает поиск с
   подтверждённой проекцией, проверяет совпадение внешних ID в том же пространстве,
   при необходимости читает карточки. Противоречия, неоднозначность и отсутствие
   внешних ID не разрешаются подбором номера или совпадением одного имени.
8. Только после проверки выполняется `GET /api/anime/2529/characters` для
   Shikimori `269` или `GET /api/anime/3061/characters` для Shikimori `20`.
   Далее `parseAnimetkaCharacters` проверяет массив и обязательные поля.
9. Tenrai запрашивается по отдельному MAL ID, полученному из карточки провайдера
   или успешного Shikimori. При отсутствии MAL ID он пропускается; равенство
   номеров Shikimori/MAL не предполагается. Это объясняет, почему Tenrai не всегда
   может компенсировать одновременно недоступный Shikimori и упавший поиск Аниметки.
10. Результаты объединяются; роли принадлежат появлению в текущем аниме.
    Подробности персонажа используют `/api/anime/characters/{characterShikimoriId}`.
    Изображения запрашивает Coil отдельно от JSON. Кнопка повтора вызывает
    `retryExtras()` с `forceRefresh=true`.

`ProviderEndpointRegistry` участвует в клиенте Аниметки: может отключить источник
или выбрать доверенное зеркало. Значение на конкретном устройстве неизвестно.
Теперь отключение явно отражается как `DISABLED`, а не как отсутствие персонажей.

## Изменения

- Удалены только два неподдерживаемых поля проекции; ID и маршрут персонажей
  не захардкожены под Bleach. Опциональные внешние ID из полученных карточек
  продолжают читаться, если реально присутствуют.
- Добавлены структурированные события с источником, этапом, состоянием, причиной,
  HTTP-кодом (когда получен), количеством записей и отдельными числовыми
  ID аниме Shikimori/Аниметки/MAL/AniList на этапе сопоставления. Причины различают HTTP, DNS,
  TLS, тайм-аут, сеть, GraphQL, формат ответа, отключение, отсутствие ID и отсутствие
  подтверждённого соответствия. Пропуск Tenrai без MAL ID виден отдельно.
- Перехватчики фиксируют фактический статус HTTP для поиска, карточек, списков,
  GraphQL и изображений. Успех из кеша или отказ до HTTP не получает выдуманный код
  200; отсутствие HTTP отмечается `none`. Ошибка JSON видна отдельным событием
  после HTTP-события соответствующего этапа.
- В Logcat используется тег `AnimeVaultCharacters`. В секции ошибки есть кнопка
  «Диагностика», показывающая безопасную сводку причин. Общее сообщение больше не приписывает
  все сбои соединению. Пример ключевых полей событий:

  ```text
  source=SHIKIMORI stage=GRAPHQL state=ERROR http=522 reason=HTTP_ERROR count=none
  source=ANIMETKA stage=SEARCH state=ERROR http=500 reason=HTTP_ERROR count=none
  ```

  Это пример формата воспроизводимого старого сбоя, не лог с устройства пользователя.
- Диагностика содержит только перечисления и числа. URL, query, заголовки,
  тексты запросов/ответов, сырые сообщения исключений и стеки не выводятся.
  Сбой приёмника диагностики не прерывает сетевую загрузку.
- HTTP-ошибка и объект ошибки вместо поискового массива не становятся успешным
  пустым поиском. Настоящий `[]` списка персонажей остаётся успешным пустым результатом.
- Проверен существующий кеш: ошибки источников уже исключаются из двухчасового
  агрегата через `hasLoadErrors`; отрицательное сопоставление не сохраняется.
  При ошибке обновления остаётся предыдущий список; повтор обходит кеш. Эти
  свойства сохранены и дополнительно проверяются фиктивными сценариями.
- Ссылки и дисковый кеш изображений сохранены. Добавлены безопасные HTTP-события
  и событие сбоя загрузки/декодирования постера; отсутствие картинки не меняет JSON.
- Версия, подпись, механизм обновления, workflows и остальные функции не изменены.

## Регрессионные тесты и лёгкие проверки

Добавлены 10 Kotlin/JUnit-сценариев с перехватчиком фиктивного API:
Bleach/Naruto после 522 с отказом на неподдерживаемые поля; HTTP 500 поиска и
восстановление; успешный пустой массив; повреждённый список и повтор; объект ошибки
при HTTP 200; отдельные пространства MAL/Shikimori; отсутствие ID/отключение;
старый список при сбое обновления; отсутствие секретов в диагностике; сбой логгера.
Существующая проверка URL также запрещает оба неподдерживаемых поля.
Фикстуры поиска специально содержат другой тайтл первым.

Выполнены только лёгкие проверки:

- `python3 -m unittest discover -s tools -p 'test_character_api_contract.py' -v`:
  3 теста проходят. Проверяется реальная проекция из Kotlin-файла на фиктивном
  контракте с записанными ответами: прежняя проекция отвергается, новая принимается.
- `bash tools/verify-final.sh` и `bash tools/verify-2.0.0.sh`: успешно.
- Tree-sitter проверяет синтаксис изменённых и новых Kotlin-файлов: ошибок нет.
  Это синтаксический разбор, не проверка типов и не компиляция Kotlin.
- `git diff --check`: успешно.

## Что без устройства и сборки не проверено

Kotlin/JUnit-сценарии добавлены, но **не запускались**, поскольку в этой задаче
запрещён Gradle. Android-компиляция, lint, APK, SDK, эмулятор и установка не
запускались. Успешная сборка/работа на устройстве здесь не заявляется.

Пользователь подтвердил Kodik, но нет лога с устройства: нельзя подтвердить
фактически переданные ID, локальную конфигурацию/кеш, доступность доменов из его
сети, поведение Coil на устройстве и точное время переключения на резерв.
Измерения HTTP относятся к сети Codex и не доказывают общую недоступность Shikimori.
Для родной карточки Аниметки или иной причины новые события позволят определить
конкретный этап вместо общего сообщения о соединении.
