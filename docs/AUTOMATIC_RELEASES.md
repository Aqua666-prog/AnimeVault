# Автоматические релизы AnimeVault

После слияния изменения версии в main больше не нужно создавать тег/Release,
загружать APK/JSON или составлять список объединённых PR вручную.

1. В PR укажите новую versionName/versionCode в `app/build.gradle.kts`.
2. Объедините PR в main.
3. `Build AnimeVault APK` выполнит прежние unit-тесты, lint, сборку с прежним
   ключом и проверки APK. Должны пройти также оба onboarding job (API 24/35).
4. Отдельный `publish-release` получит артефакт **из этого же запуска**,
   повторно проверит исходники, APK, SHA-256, JSON и целевой тег.
5. Он создаст `v<versionName>` на точном SHA сборки, затем draft Release,
   загрузит `AnimeVault.apk` и `animevault-update.json` и опубликует релиз как latest.
   Заголовок содержит версию и код; описание создаётся GitHub Generate Release Notes.

Сама versionName/versionCode автоматически не повышается: она остаётся частью
проверяемого PR. Файл `RELEASE_X.Y.Z.md` для публикации не обязателен.

## Ограничители

- Только push в main публикует. Ручные и тестовые сборки, push тега — без публикации.
- Для main целевой тег автоматически вычисляется перед сборкой из исходников;
  обязательное сравнение после сборки сохраняется. JSON по-прежнему создаётся
  из собранного APK. Значения версии вручную в workflow не задаются.
- Сериализован только job публикации; он ждёт успешного build и всей матрицы
  onboarding. При любой ошибке проверок публикация пропускается.
- Устаревшая сборка, чей SHA уже не HEAD main, пропускает публикацию.
- Опубликованный релиз не перезаписывается, даже при повторном запуске на той же
  версии. Для следующего выпуска нужна новая версия.
- versionCode нового выпуска должен превышать код из JSON текущего latest.
  Отсутствующий/нечитаемый JSON latest останавливает выпуск до исправления данных.
- Существующий тег другого SHA не перемещается. Чужой draft не редактируется.
- Повторный запуск может продолжить только собственный draft того же SHA.
  До успешной загрузки обоих файлов релиз остаётся черновиком.
- Автоматический токен `GITHUB_TOKEN` получает `contents: write` только в publish
  job; новый персональный токен не нужен. Секреты подписи не меняются.
- Удалён триггер `release.published`: публикация не вызывает ещё одну сборку.
  События записи через GITHUB_TOKEN также не запускают цепочку push workflow.

## Повтор и ошибки

При временном сбое публикации можно выбрать **Re-run failed jobs** у исходного
запуска, если его SHA по-прежнему HEAD main. Автоматизация продолжит свой draft.
Если main уже изменился, публикуется актуальная успешная сборка. При конфликте
тега/черновика после смены SHA безопасный следующий выпуск получает новую версию;
автоматика не переносит старые теги и не переписывает готовые релизы.

Публикация использует GitHub Releases API через gh, с явным PATCH и boolean
`draft=false`. Только HTTP 404 считается отсутствием релиза/тега; ошибки сети
и доступа не трактуются как отсутствие данных.

## Проверки изменения

- 13 новых офлайн-тестов publisher: создание/порядок операций, повтор, ошибка
  upload, запрет чужого draft/тега, проверка JSON/hash, monotonic versionCode,
  401/403/сетевая ошибка против 404, PATCH/boolean, main preflight и CLI guard.
- 13 существующих тестов версий и 7 тестов генератора JSON: успешно.
- YAML, Bash всех run-блоков и Python: синтаксис проверен.
- `verify-final.sh`, `git diff --check`: успешно.
- Шаги восстановления ключа, проверки подписи, сборки, unit-тестов, lint и вся
  матрица onboarding сравнены с main: без изменений.
- Приложение и его версия **3.0.9 (69)** не менялись: это изменение CI.

Ни один настоящий Release/тег в Codex не создавался. Gradle, Android SDK,
эмулятор, APK/AAB не запускались. Реальные права GITHUB_TOKEN, доступность gh/API,
публикация и совместимость APK должны подтвердиться первым успешным запуском
Actions после слияния PR. Исторические опубликованные файлы эта автоматизация
не исправляет и не заменяет.

Изменённые файлы: `.github/workflows/build-apk.yml`,
`tools/publish-github-release.py`, `tools/test_publish_release.py`, `README.md`,
`docs/AUTOMATIC_RELEASES.md`.
