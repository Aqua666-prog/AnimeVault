# AnimeVault 4.0 — публичная облачная платформа

## Статус
Phase 1 — backend MVP. Это **не production-ready** сервер. Android-клиент пока не подключён к API; работающая версия 3.0.3 сохраняется без изменений.

## Цели
- Не ломать существующие Media3, Room, офлайн-загрузки, AniList и адаптеры провайдеров.
- Позволить пользователю зарегистрироваться, войти и хранить личный список просмотров на сервере.
- Синхронизировать данные между устройствами по устойчивым ID аниме.
- Сохранять доступ к локальной медиатеке без аккаунта и интернета.
- Использовать только источники видео, доступ к которым разрешён правообладателями и условиями API.

## Архитектура
Android (Compose / Retrofit / Room) -> HTTPS -> FastAPI -> PostgreSQL.
На первом этапе видео остаётся на стороне текущих провайдеров; сервер **не проксирует и не хранит видео**.
JWT access tokens действуют 30 минут. Пароли хешируются Argon2 через pwdlib.
Секреты передаются только через окружение; никакие токены и пароли не коммитятся.

## API v1 (реализованная серверная часть)
- `GET /health` — техническое состояние процесса.
- `POST /v1/auth/register` — email/password -> access token.
- `POST /v1/auth/login` — email/password -> access token.
- `GET /v1/me` — профиль текущего пользователя.
- `GET /v1/library` — список записей текущего пользователя.
- `PUT /v1/library/{anime_id}` — создать/обновить статус, номер серии и позицию.
- `DELETE /v1/library/{anime_id}` — удалить запись.

`anime_id` в MVP означает **AniList ID**, а не внутренний ID провайдера. При отсутствии AniList ID клиент не должен подменять его случайным идентификатором.

## Следующая итерация — Android integration
1. Экран входа/регистрации в Compose, отдельная модель состояния.
2. Retrofit API и токен в Android Keystore-backed encrypted storage; исключить логирование секретов.
3. Очередь изменений Room -> сервер при наличии сети через WorkManager.
4. Первоначальная загрузка сервера -> локальная БД с явным подтверждением слияния.
5. Конфликты: `updated_at` и версия записи; предусмотреть идемпотентность и tombstones для удалений. Пока в MVP действует last-write-wins на сервере, **полноценной двусторонней синхронизации нет**.
6. Logout, истечение токена, восстановление сеанса и обработка ошибок.

## Требования перед публичным запуском
- Подтверждение email, восстановление пароля, безопасные refresh tokens с ротацией и отзывом.
- Rate limiting регистрации/логина, антиспам, аудит безопасности, мониторинг и резервные копии.
- Alembic миграции вместо `create_all`; отдельные тестовая и production БД.
- Политика конфиденциальности, удаление аккаунта и экспорт пользовательских данных.
- TLS на reverse proxy, домен, настройка CORS (только если появится web frontend), секреты в менеджере секретов.
- Тесты многопользовательской изоляции, нагрузочные тесты и проверка миграций.
- Соблюдение условий API и прав на контент.

## Локальный запуск
```bash
cd server
python -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
export JWT_SECRET="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')"
uvicorn app.main:app --reload
pytest -q
```
По умолчанию используется локальная SQLite для разработки. Для PostgreSQL задайте `DATABASE_URL`.
Для Docker Compose задайте `POSTGRES_PASSWORD` и `JWT_SECRET` в окружении, затем `docker compose up --build`.
Compose слушает только localhost:8000; для публичного доступа требуется HTTPS reverse proxy.

## Критерии приёмки этапа 1
- Новый пользователь регистрируется, получает JWT, входит и читает свой профиль.
- Повторная регистрация email отклоняется.
- Один пользователь не может видеть или удалять записи другого.
- Можно записать и получить статус, серию и позицию просмотра.
- Ошибочные параметры отклоняются.
- Существующее Android-приложение продолжает собираться без изменений.
