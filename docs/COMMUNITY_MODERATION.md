# Community: модерация и удаление данных

Android-панель модератора в этой версии отсутствует. Минимальная административная основа — защищённые RPC и Supabase SQL Editor, доступный доверенному владельцу.

## Первый администратор

1. Создать и подтвердить отдельный Community Account.
2. В Supabase Dashboard → Auth проверить пользователя и получить точный UUID.
3. Через доверенный SQL Editor как владелец выполнить (заменить UUID):

```sql
insert into public.community_private_roles(user_id,role,granted_by)
values ('00000000-0000-0000-0000-000000000001','admin',null);
```

Назначение не основано на никнейме/email из клиентского запроса. Пользовательские metadata, Firebase UID и локальные флаги не учитываются. Дальнейшие назначения/отзывы выполняет владелец тем же доверенным способом, записывая административное основание в операционный журнал. Не выдавать service_role Android-приложению.

## Работа с жалобами

Использовать JWT назначенного Community-модератора при вызове RPC. Если работа ведётся в доверенном SQL Editor владельца, в транзакции явно установить проверенный UUID модератора:

```sql
begin;
select set_config('request.jwt.claim.sub','00000000-0000-0000-0000-000000000001',true);
select public.community_review_reports(0); -- максимум 50, далее offset
-- Использовать конкретный проверенный UUID жалобы/комментария из результата.
-- select public.community_moderate('<comment UUID>', 'hide', 'Причина скрытия');
-- select public.community_moderate('<comment UUID>', 'restore', 'Результат апелляции');
-- select public.community_ban('<user UUID>', 'Повторный спам', now()+interval '1 day', false);
-- select public.community_ban('<user UUID>', 'Бессрочная блокировка', null, false);
-- select public.community_ban('<user UUID>', 'Апелляция удовлетворена', null, true);
select public.community_review_log(0);
commit;
```

Проверка роли остаётся внутри функций. Модератор не блокирует другого носителя доверенной роли. Статус deleted не восстанавливается. Hide/restore закрывает активные жалобы как reviewed и пишет moderation log; ban/unban также журналируются. Для отклонения жалобы без действия доверенный владелец может обновить её status на dismissed через SQL Editor, фиксируя решение в своём журнале. Жалобы/UUID заявителя не публичны.

## Канонические тайтлы и серии

Только доверенный оператор заводит `community_anime` с подтверждённым AniList/MAL и отдельные `community_anime_aliases`. Сверять сезон, формат, год, оригинал/ремейк и официальные внешние ссылки. Одинаковое название недостаточно. Unique constraints не позволяют присвоить одному внешнему ID несколько тайтлов. Неверное соответствие сначала снять с `verified`, проверить влияние на уже существующие обсуждения, исправить в согласованной транзакции; не перепривязывать историю автоматически.

`community_episodes` создаются внутри конкретного canonical anime. Примеры episode_key: `regular:12`, `special:12.5`, `ova:1`. Для каждого провайдера внести отдельно проверенную `community_episode_aliases` с точными release/episode ID, используемыми адаптером приложения. Нельзя строить связи из похожих названий или целой части дробного номера. Без verified alias UI покажет недоступность.

## Запрос удаления аккаунта

1. Проверить заявителя через доверенный канал и повторную аутентификацию; сопоставить именно Supabase UUID. Не принимать произвольный UUID/email в открытом Android RPC.
2. Объяснить, что Google/Firebase-аккаунт и локальная медиатека удаляются отдельно. Уточнить необходимость удаления личного текста из обсуждений.
3. Сделать доступную владельцу резервную копию в соответствии с политикой хранения и записать основание операции.
4. Только через доверенный SQL Editor выполнить `select community_internal.erase_account('<verified UUID>');` в согласованной транзакции.
5. Проверить: Auth user и профиль удалены, авторство обнулено, содержимое его комментариев заменено placeholder, description его жалоб очищен; его лайки, роли и ban удалены по FK; чужие ответы сохранены.
6. Если Auth user удаляется через Dashboard, before-delete trigger профиля также очищает текст/описания до FK-анонимизации. Проверить это в staging перед использованием в production.
7. Отозвать/проверить завершение его сессий через поддерживаемые инструменты Auth. Access JWT может жить до истечения срока, но запись нового комментария требует существующего профиля. Установить документированную политику retention/audit/backup для причин модерации и логов; при наличии персонального текста очистить его отдельно, сохраняя необходимый законный аудит.
8. Попросить пользователя выйти из Community на устройствах, очистить локальные данные приложения при необходимости. На удалённых офлайн-устройствах старый кеш нельзя отозвать мгновенно; срок кеша ограничен 7 днями. Сроки удаления резервных копий определяет владелец.

Внутренняя erase_account не доступна anon/authenticated и не является обходным публичным удалением пользователя. В APK нет административных credentials.
