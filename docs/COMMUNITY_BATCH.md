# Ограниченная массовая публикация Community

Режим `batch` использует существующие очередь discovery, HTTP-клиент, `community_sync_batch` и `community_resolve`. Canary остаётся отдельным. Новых миграций, изменений Android и новых Secrets нет. Discovery теперь только читает источники; прежний неограниченный job публикации удалён из workflow. Расписание запускает только discovery, не batch. Оставьте `COMMUNITY_AUTOSYNC_DAILY_WRITE=false`.

## AutoSync v2

Реальный Batch run `41425751076` сообщил `batch_chain_endpoint` для AniList212. В discovery run `41395977782`, artifact `13119656455`, alias `kodik/shiki:212` содержал material `movie-94408`, provenance `animetka_kodik_material`, Animetka608, но `evidence.url` указывал на AniMetka вместо Shikimori. Импортёр перезаписывал URL цепочки при добавлении provenance. Это локальная ошибка формата доказательства, не HTTP-ошибка AniList. Теперь provenance имеет отдельный URL, а цепочка сохраняет Shikimori. Старый формат допускается только при точном соответствии provenance/material/Animetka endpoint и обязательной новой проверке первичных API. Публичные GET Shikimori212 и AniMetka608 во время аудита вернули HTTP200, MAL212 и material movie-94408 соответственно. Fresh AniList/Kodik с настроенным токеном проверяются в owner-run workflow.

Полностью существующие canonical/verified aliases проверяются resolver и не отправляются повторно даже после потери checkpoint. Для новой связи у существующего аниме `writes` содержит только alias: это один элемент лимита. Необязательное обновление названия не расходует лимит. `items` в плане остаётся полным контекстом проверки, а `writes` — точным payload будущей RPC. Изменение приватного состояния между plan/apply блокирует запись.

Batch пытается найти Kodik-связь и для канонических записей без cached alias: целевой запрос по кандидату Shikimori ID, затем обязательная явная ссылка Shikimori → MAL и проверка AniList. Равенство числа MAL и Shikimori не считается доказательством. Если их числовые ID различаются, такой поиск может не найти связь; нужны discovery/доверенный мост. Пустой ответ не создаёт alias; временная ошибка поиска сохраняется в отчёте и не мешает безопасной публикации подтверждённой canonical-only записи. Конфликт ID останавливает план целиком.

## Что разрешено

`max_publish_items`: **5, 10, 25, 50, 100**. Это сумма элементов `p_items`, фактически отправленных за весь запуск: anime и alias считаются отдельно. Новая пара занимает 2 элемента, новая каноническая запись без alias — 1; только новый alias у существующего аниме — 1. Поэтому 5 — не пять аниме с пятью aliases. При остатке 1 пара переносится на следующий запуск. Повторные HTTP-отправки записывающего RPC внутри одного запуска отключены: при неопределённом результате запуск останавливается.

Канонические записи требуют обоих ID и свежего ответа AniList, подтверждающего их вместе. Aliases допускаются только verified с точным Android-контрактом. Поддерживаются Kodik material → Shikimori → MAL → AniList; AniMetka detail → явные MAL/Shikimori → AniList; Yummy detail remote_ids → MAL/Shikimori → AniList; AniLiberty release → подтверждённые UUID эпизодов в AniMetka mapping → Shikimori → MAL → AniList. UUID используются для проверки связи релиза, не для публикации серий. Сохранённый material ID должен находиться в свежем ответе Kodik. Совпадение названий/номеров серий нигде не является доказательством. Серии и pending/rejected не публикуются. AnimeVost и HTML-источники без независимых ID остаются в discovery; сходство названий и номера серий не дают права на публикацию alias. AniLiberty без подтверждённого моста также остаётся непубликуемым кандидатом.

## Запуск с Android-телефона

1. После merge PR откройте GitHub → AnimeVault → **Actions → Community Catalog AutoSync → Run workflow**, ветка **main**.
2. Если нет свежего discovery: сначала `mode=discovery`, apply выключен. Дождитесь успешного `catalog-discovery`. Batch выбирает артефакт успешного main-запуска, никогда PR.
3. Выберите `mode=batch`, `max_publish_items=5`, **apply выключен**, confirmation пустой. Запустите новый workflow. В Summary/artifact `batch-plan` проверьте `batch-report.json`: точные `groups.items`, исходное состояние, ошибки и количество `records`. Public dry-run не видит скрытые/unverified aliases.
4. Для записи задайте Repository Variable `COMMUNITY_AUTOSYNC_WRITE_ENABLED=true`; `COMMUNITY_AUTOSYNC_DAILY_WRITE=false`. Существующие `SUPABASE_PUBLISHABLE_KEY`, Secrets `KODIK_API_TOKEN` и `SUPABASE_SERVICE_ROLE_KEY` остаются теми же. Для Yummy используется уже существующий `YUMMY_APPLICATION_KEY`; без него Yummy-кандидат отклоняется с причиной. Не вводите ключи в workflow inputs, Issues или чат.
5. В Environment **community-catalog-write** должны быть Required reviewers и разрешена только main. Workflow проверяет наличие reviewer-правила до записи; недоступная проверка блокирует запуск.
6. Новый запуск: mode=batch, лимит 5, apply включён, `batch_confirmation=PUBLISH BATCH 5`. Для другого лимита число в фразе обязано совпадать. Canary confirmation оставьте пустым.
7. Сначала job plan создаст новый dry-run без service_role. Просмотрите план **этого запуска** перед approval Environment. Затем одобрите deployment с телефона. Publish привязан к hash плана, run ID и attempt; подмена артефакта/повтор старого approval не допускается.
8. Publish повторяет свежие доказательства и public preflight, затем выполняет admin preflight, видящий все aliases. При изменении состояния/конфликте останавливается. Перед каждой RPC в логе показан финальный dry-run. Ключи, query parameters и тела ошибок источников не выводятся.
9. Скачайте `batch-result`. `published` — элементы writes, принятые RPC в этом запуске; `resolved` — элементы групп, прошедших read-only проверку. Проверяются **все**, а не только выборка: canonical resolver и для каждой пары точный Android resolver должны вернуть один UUID без episode.
10. После успешной партии проверьте обсуждения в приложении. Увеличивайте лимит постепенно: 5 → 10 → 25 → 50 → 100. Это ручные подтверждаемые партии, не автоматическое разрешение ежедневной записи.

## Checkpoint, ошибки и повтор

Checkpoint `batch-checkpoint.json` содержит digest подтверждённых групп и `_scan_after` — курсор детерминированного обхода, без токенов. Plan сохраняет курсор даже при dry-run, чтобы длинный существующий/ошибочный префикс не мешал следующим кандидатам; этот курсор не является подтверждением публикации. Полные successful digests не мешают поиску нового alias для существующего аниме. Сохраняется после каждой успешной resolver-проверки, атомарной заменой файла; переносится через отдельный GitHub cache `batch-v1-*` и artifacts. `if: always()` сохраняет прогресс при штатной ошибке. План также сохраняет checkpoint cache; publish сохраняет более новый checkpoint после resolver. Read-only HTTP-запросы сохраняют ограниченные повторы/backoff, а записывающая RPC не повторяется автоматически; после неё параметры повторов чтения восстанавливаются даже при ошибке. Cache может быть удалён GitHub; при жёсткой остановке runner последний checkpoint может не загрузиться. Серверный журнал RPC остаётся защитой: стабильный UUID от содержимого группы возвращает прежний receipt вместо дубликатов. Истечение cache может вызвать повторные проверки/отправки уже существующих записей, но не дубликаты.

После transport error неизвестно, завершилась ли серверная транзакция: публикация останавливается; не выполняйте ручное удаление. Следующий **новый** запуск повторит preflight и идемпотентную RPC. Сервер сохраняет конфликтующий alias и возвращает rejected, который не считается успехом и не попадает в checkpoint. Каноническая часть такой пары могла быть принята — `failed` не означает rollback всего запуска. Каждый RPC транзакционен; весь запуск состоит из отдельных групп. Ранее успешные группы сохраняются при поздней ошибке.

Отчёт: `discovered` — число канонических записей discovery; `verified/pending/rejected` — состояния aliases discovery; `failed` и `errors` включают проверки кандидатов и ошибки публикации; `published/resolved/submitted` относятся к текущей публикации. Поля не являются взаимоисключающими итогами одной таблицы. Ошибка preflight в plan пропускает кандидата с причиной; число проверяемых кандидатов ограничено `max(20, limit*2)` для ограничения нагрузки. Конфликт/ошибка в publish останавливает остальные группы. Пустой план допустим и ничего не отправляет.

Настройка Environment и реальный publish требуют проверки владельцем после merge. Codex production не изменяет. Миграции 001/002 повторно не применять.

## Отчёт v2 и проверка из Android

Дополнительно: `new_canonical`, `new_aliases`, `canonical_updates`, `alias_updates`, `existing_canonical`, `existing_aliases`, `existing`, `ambiguous`, `rejected_candidates`, `provider_errors`, `kodik_no_match`. New/update — планируемые мутации после preflight, не заявление о production INSERT. `canonical_resolved` и `android_resolved` разделены: canonical-only успех **не** подтверждает доступность обсуждения из карточки провайдера. `failed` включает upstream/validation failures; причины в errors с source/stage/status. При конфликте план блокируется без write job.

Android не изменён: OnlineTitleScreen передаёт release.providerId/release.id и реальные MAL/AniList метаданные; AnimeIdentityResolver передаёт их в RPC. SQL при provider != null требует verified alias и согласованность metadata, без fallback на похожий тайтл. Kodik releaseReference отдаёт shiki перед kp/material. AniMetka/Yummy используют числовой primary ID, AniLiberty — release.id.

После owner-run Batch100 проверьте `android_resolved` и несколько конкретных карточек **в выбранных источниках**, не Unified synthetic source: Community → список комментариев → публикация/ответ/лайк при отдельной Community-сессии. Для карточки без alias ожидается недоступное обсуждение, не чужая ветка. Реальный UI/TalkBack/устройство в Codex не запускались. Auth/комментарии/лайки/ответы, SQL/RLS и версия 4.1.1(81) не изменялись.

**Batch100 dry-run с телефона:** Actions → Community Catalog AutoSync → Run workflow → main → mode=batch → max_publish_items=100 → apply=false → оба confirmation пустые. Для последующего нового apply-run нужно `PUBLISH BATCH 100`, unchanged daily=false и approval защищённого Environment; сначала изучите план именно этого запуска. Обновите discovery, если последний артефакт устарел: batch не может подтвердить отсутствующие в primary API связи. Никто не запускает production-публикацию из Codex.
